# 零碳农业园区融合版V2项目交接手册

## 1. 交付结论与平台定位

本平台面向“基于绿电直连的零碳农业园区优化调度策略”第一阶段，统一承载农业生产、能源监测、预测、日前与滚动调度、绿电直连、规划分析、碳核算、资产、数据、报表和系统管理。融合版页面采用深色能源驾驶舱风格，导航按业务域组织，共1个态势总览和77个业务页面。

当前版本已经形成可启动、可测试、可部署、可演示和可继续开发的项目骨架。计算结果来自农业园区参数登记表、年度时序、能量流、固定容量策略、规划优化、绿电合同结算、压力测试和预测服务，不再在页面中散落固定数字。所有金额统一使用人民币，能量统一使用兆瓦或兆瓦时，碳排统一使用吨二氧化碳。

> **交付边界：**当前可交付形态为单节点SQLite持久任务仓储，适合本机演示、受控内网试点和单节点项目交付。25张PostgreSQL项目级目标表已经提供，但业务仓储适配器尚未切换；没有接入现场表计、生产管理系统、气象服务、交易结算或企业统一身份认证，因此所有标记为“演示参数”或“待补充”的数据不得作为正式投资决策依据。

## 3. 平台业务边界

### 3.1 零碳判定边界

第一阶段采用“园区运营用电边界”。核算对象包括灌溉、粮食加工与烘干、仓储冷链和公共辅助四类电负荷；供给包括园区光伏、绿电直连、储能放电和公共电网购电。零碳判定要求年度剩余普通电网购电对应排放不超过0.01吨二氧化碳的数值容差，并且绿电属性可核验。

建设期隐含碳、农业投入品、运输、农机燃油、甲烷和氧化亚氮目前不在第一阶段零碳结论内。页面必须把“运营用电零碳”和“全生命周期零碳”分开表达。

### 3.2 能量流方向

每个时间步均按同一物理顺序结算：农业负荷提出用能需求；园区光伏优先直接供负荷；绿电直连按合同曲线、通道能力、线路损耗和可用率送达；剩余绿电可为储能充电；储能在功率、能量、效率和荷电状态边界内放电；不足部分由公共电网补足；仍有富余才允许外送或弃电。

电功率平衡为：

`园区光伏直供 + 直连绿电送达 + 储能放电 + 电网购电 = 农业负荷 + 储能充电 + 外送 + 弃电`

储能状态递推为：

`SOC(t+1) = SOC(t) + 充电功率×充电效率×步长/能量容量 - 放电功率×步长/(放电效率×能量容量) - 自放电`

直连送达功率为：

`送达功率 = min(送端可用功率, 合同计划, 通道容量) × (1 - 线路损耗率) × 可用状态`

### 3.3 绿电属性与防重复计算

光伏、直连绿电、普通电网和储能充电来源分别记账。储能放电继承充电来源属性，不把普通电网充入储能后的放电误记为绿电。绿证抵扣和物理直连供电不得对同一兆瓦时重复计入；当前演示结果的绿证抵扣量设置为0。

### 4.2 参数来源分级

参数登记表采用五级来源：A级为计量实测，B级为合同、铭牌或报价，C级为政府及官方资料，D级为工程计算，E级为演示假设。每个参数同时保存编码、名称、分组、单位、当前值、上下限、来源等级、核验状态、来源引用和设置方法。

正式项目上线前，应先补齐A级和B级数据，再由工程师完成D级计算。E级参数只能用于功能演示和方案方法验证，不能直接用于招采、投资和对外承诺。完整参数台账见本手册附录B，并可通过`GET /api/v2/parameters`读取。

### 4.3 数据替换顺序

1. 接入园区总表和四类负荷分表，完成15分钟数据对齐、缺失标记和日电量校核。
2. 接入光伏逆变器、储能变流器与电池管理系统、直连线路两端表计。
3. 导入电价、需量、绿电合同、偏差考核、容量费用和设备报价。
4. 导入农业日历、地块、泵站、批次、含水率、库存和温控边界。
5. 用至少一个完整生产季回测预测、调度和收益结果，并冻结正式参数版本。

## 5. 计算与算法实现

### 5.1 年度农业时序

`src/model/agri_park_profiles.py`生成全年15分钟或小时级曲线。算法以季节窗口、工作班次、气温代理、秋收增量和归一化日型构造四类负荷，再校准到登记表中的年电量和峰值。该方法确保曲线具有农业时段逻辑，但在现场数据接入前仍属于合成基准。

### 5.2 预测中心

`ForecastService`按历史曲线生成负荷、光伏、直连供给、气象、电价和农业任务预测。当前基线使用季节与时段特征、滑动趋势和确定性扰动形成预测，并计算平均绝对误差、均方根误差和平均绝对百分比误差。没有概率分布训练样本时，平台不会宣称真实P10、P50、P90概率预测，只展示演示区间并标注数据边界。

正式升级建议采用：负荷使用LightGBM或时序Transformer并加入农业日历；光伏使用数值天气预报和物理功率模型；冷链加入温度、库存和开门事件；所有模型采用滚动时间切分回测、基线模型对照和漂移监控。

### 5.3 固定容量快速调度

`AgriEnergyFlowService`在给定光伏、储能和直连容量下进行逐时间步能量分配，遵守功率平衡、SOC、效率、通道损耗和进出口上限。它用于总览、实时监测、策略比较和演示级快速计算，优点是稳定、可解释、速度快，缺点是不搜索最优容量。

### 5.4 V17综合能源规划

`AgriZeroCarbonOptimizer`在容量搜索空间中联合选择光伏容量、储能功率、储能能量和直连合同容量，并调用年度调度计算候选方案。目标函数最小化年化总成本：

`年化投资 + 固定运维 + 购电费 + 需量费 + 直连电量及容量费用 + 偏差考核 + 储能衰减 + 弃光惩罚 + 未供电惩罚 - 外送收益`

约束包括供需平衡、变压器与进出口能力、光伏和储能规划上限、SOC边界、充放电效率、等效循环、直连容量与最低消纳、供电不足比例、备用率、零碳目标和农业任务时间窗。V17模式用于中长期容量规划和多方案比较，不等同于现场控制器。

### 5.5 日前与滚动优化

日前计划使用未来24小时96点预测，给出能源来源、储能、柔性负荷、备用、成本和碳排。滚动优化每15分钟刷新状态和未来窗口，固定已经执行的决策，只调整尚未执行部分。人工锁定、农业截止时间、冷链温控和设备安全边界优先级高于经济性。

### 5.6 绿电直连合同结算

`GreenDirectBenefitService`在相同负荷基准下比较五类策略：普通电网基准、经济型直连、平衡型直连、推荐规划和运营用电零碳。结算包含送端计划、受端送达、线路损耗、最低消纳、计划偏差免考核区间、超限偏差费用、通道容量年费、输配及辅助服务费和线路可用率。

收益拆解严格满足：

`总成本变化 = 电量费用变化 + 需量费用变化 + 投资年化变化 + 运维变化 + 合同费用变化 + 偏差考核变化 + 储能衰减变化 + 可靠性价值变化 + 其他项`

归因表执行精确对账，避免“各项收益相加不等于总收益”。内部收益率只有在存在正向年度现金节约且现金流发生符号变化时才计算；不满足条件时显示“不适用”，不制造理想化回报率。

### 5.7 碳核算

运营电力排放按普通电网净购电量乘以0.55吨二氧化碳/兆瓦时的演示排放因子计算；园区光伏和物理直连绿电在运营电力口径下记为零。减排量等于基准排放减去方案排放。正式项目应替换为适用年度和区域的官方排放因子，并保留因子版本和证据附件。

### 5.8 压力测试

固定同一组容量，不重新优化，依次施加低辐照、负荷升高、直连降额、储能不可用、电价上涨、设备故障和组合极端场景。输出成本、碳排、未供电、最大需量、绿电比例和约束状态。固定容量是为了暴露方案脆弱性；若每个场景都重新选容量，会掩盖真实风险。

## 6. 两种模型模式的区别

| 对比项 | 快速调度模式 | V17综合能源规划模式 |
|---|---|---|
| 决策对象 | 已给定设备容量下的能量流 | 同时选择容量并计算年度运行 |
| 时间尺度 | 当前日、代表日或固定年度 | 年度8760时序与规划周期 |
| 主要用途 | 实时演示、监测、策略快速比较 | 容量配置、投资比较、零碳路径 |
| 速度 | 秒级或缓存后即时 | 首次计算约几十秒，缓存后即时 |
| 约束重点 | 功率平衡、SOC、通道与设备边界 | 快速调度约束加投资、可靠性、零碳和规划边界 |
| 输出 | 负荷、供给、SOC、成本、碳排 | 推荐容量、全寿命成本、收益、碳排、压力测试 |

“综合规划模式下，本页直接读取V17优化结果”表示绿电直连页面不再另设一套固定容量和固定收益数字，而是复用同一次V17方案的容量、年度调度和成本结果。这样可以保证规划页、绿电页、碳页和报表页口径一致。

## 7. 结果基线与合理性说明

当前演示基准刻意保留“不一定越绿越便宜”的结果，防止过度理想化。相对于普通电网基准，经济型直连可降低年度成本；随着绿电比例提高，固定工程费、容量费和新增设备投资可能使年成本上升；运营用电零碳方案在当前演示参数下成本最高。页面应同时展示成本、绿电比例、排放、需量、弃电、未供电和合同风险，不能只展示单一“节省金额”。

| 策略 | 年成本 | 相对基准 | 绿电比例 | 年排放 |
|---|---:|---:|---:|---:|
| 普通电网基准 | 679.88万元 | 0 | 0% | 4896.30吨二氧化碳 |
| 经济型直连 | 557.92万元 | 节省121.96万元 | 30.61% | 3397.55吨二氧化碳 |
| 平衡型直连 | 776.50万元 | 增加96.62万元 | 47.71% | 2560.49吨二氧化碳 |
| V17推荐规划 | 798.60万元 | 增加118.73万元 | 48.13% | 2539.73吨二氧化碳 |
| 运营用电零碳 | 833.15万元 | 增加153.27万元 | 100% | 0吨二氧化碳 |

这些数值是演示参数下的方法结果，不是项目承诺值。正式报告必须同时附参数版本、数据周期、模型版本、求解状态、约束违反量和压力测试结果。

### 9.2 项目任务接口

项目、场景和优化任务使用`/api/v1`接口。提交任务后，API写入持久仓储，Worker以原子方式领取任务，持续更新租约和心跳，写入结果或结构化错误。幂等键避免重复提交；超时任务未达到最大尝试次数时重新排队，达到上限后失败并等待人工处理。

## 10. 数据库与扩展策略

当前SQLite启用WAL模式，数据库文件、成果文件和备份目录通过数据卷持久化。它适合单节点，但不适合多API实例共享写入。

`deploy/postgres/init/001_v2_schema.sql`定义25张目标表，覆盖组织园区、用户角色、项目场景、参数版本、模型版本、资产、计量点、遥测、预测、生产任务、优化作业、调度计划、指令、碳账本、合同、报表、告警、审计和备份。下一阶段需实现PostgreSQL仓储适配器、数据迁移脚本、双写或停机迁移、回滚和一致性校验后，才能把数据库状态标记为“已接入”。

推荐扩展顺序：PostgreSQL业务仓储；Redis或消息队列；对象存储；时序数据库或分区表；企业统一身份认证；集中日志、指标与链路追踪。

## 11. 认证、权限和审计

生产默认采用令牌模式。账号由`PLATFORM_USERS_JSON`配置，口令使用PBKDF2哈希保存，禁止提交明文。内置角色包括管理员、工程师、运行员、查看者和审计员。项目与参数写操作仅对授权角色开放；系统状态仅管理员和审计员可见；前端同时隐藏无权菜单和禁用无权导出，但最终权限以API校验为准。

审计记录登录、查询、项目场景修改、作业、状态迁移、导出和系统管理操作。令牌密钥、启动密钥和账户配置必须使用部署平台密钥管理，不得写入仓库。

## 12. 部署与启动

### 12.1 融合版容器部署

1. 复制`.env.v2.example`为`.env.v2`并设置32字符以上的认证密钥、16字符以上的启动密钥、账号哈希和允许来源。
2. 运行`docker compose --env-file .env.v2 -f compose.v2.yaml config`检查配置。
3. 运行`docker compose --env-file .env.v2 -f compose.v2.yaml up -d --build`。
4. 检查前端`http://服务器地址:8080`、API的`/health`和`/ready`。
5. 通过受控网络采集`/metrics`，并验证登录、总览、参数、任务、备份和审计。

本机未安装Docker，因此当前版本已经完成Compose结构测试、镜像文件检查和前端生产构建，但尚未在本机完成容器实机启动。正式交付环境必须补做一次构建、启动、重启和数据持久化验收。

### 12.2 本地开发启动

后端使用仓库虚拟环境执行FastAPI，前端使用锁定依赖执行Vite。开发环境可关闭认证，但只能绑定本机或受控内网；任何公网部署都必须启用令牌认证和HTTPS。

## 13. 运维、备份与故障处理

健康检查区分存活和就绪；指标输出作业状态计数；API和Worker使用单行结构化日志。SQLite在线备份同时生成数据库、成果文件和SHA-256清单。恢复操作必须进入维护窗口，停止API和Worker，校验清单后恢复，再执行健康检查和抽样结果复算。

常见故障处理：页面空白先检查浏览器控制台和API地址；接口401检查令牌和账号状态；接口403检查角色；任务停滞检查Worker、租约和日志；结果不一致检查参数版本、数据周期、模型版本和缓存；部署失败先执行Compose配置检查；数据库恢复后必须核对项目数、作业数、成果清单和审计连续性。

## 14. 测试与验收

测试分为模型、API、权限、持久化、部署结构、前端单元测试、类型检查、生产构建和浏览器验收。模型验收检查能量守恒、SOC边界、费用归因、策略排序、零碳条件和压力场景；API验收检查状态码、角色和敏感字段；前端验收检查78个路由、11个系统页面、无占位错误、无控制台异常和关键图表可见。

发布前最低验收项：后端全量测试通过；前端类型检查、单元测试和生产构建通过；代表性页面逐一打开；登录和角色权限通过；任务完整跑通；备份恢复演练通过；正式参数不含未确认E级值；所有金额均为人民币；报告带参数、模型和数据版本。

## 15. 已知限制与第二阶段任务

- 现场表计、生产任务、气象、电价和合同尚未真实接入，当前数据为可追溯演示基准。
- 预测服务是演示级确定性基线，尚未训练项目专属概率模型。
- V17容量搜索适合方案筛选，正式投资决策需要更精细的混合整数优化、设备离散选型和求解器证明。
- 当前前端多页面复用领域模板，写操作和实时推送仍需按业务逐页实现。
- PostgreSQL只有目标表结构，尚未完成业务仓储迁移。
- 当前不是高可用集群，未接入统一身份认证、消息队列、对象存储和集中监控。

第二阶段应以“真实数据闭环”优先：先接计量与农业任务，再做预测回测和滚动调度；随后接入合同结算和执行回执；最后实施PostgreSQL迁移、企业权限、高可用和正式验收。
